# debugging

버그를 고쳐달라는 요청을 받으면 바로 코드를 고치지 않는다. 아래 순서를 따른다.

## Workflow

```
1. 증상 재현/확인
2. 레이어 특정 (UI / Provider / UseCase / Repository / DataSource / API)
3. 원인 가설 수립
4. 로그·에러 메시지·스택트레이스 확인
5. 최소 재현 범위로 좁히기
6. 근본 원인 확인
7. 수정
8. 회귀 테스트
9. format / analyze
10. 검증
```

### 1~2. 증상 확인과 레이어 특정

에러가 어느 계층에서 발생했는지 먼저 특정한다 (`architecture.md`의 `UI → Provider → UseCase → Repository → DataSource → API/DB` 흐름을 따라 추적). 예를 들어 화면에 에러 메시지가 보이면, 그 메시지가 `Failure`에서 온 것인지, 위젯 자체의 렌더링 문제인지부터 구분한다.

### 3~4. 가설과 근거

추측만으로 수정하지 않는다. 로그(`print`/디버거), 스택트레이스, 관련 코드를 실제로 읽고 가설을 세운다. `NetworkException`/`Failure` 계층 어디서 매핑이 잘못됐는지 등 구체적 지점을 특정한다.

### 5~6. 최소 재현과 근본 원인

가능하면 문제를 재현하는 최소 케이스(특정 입력, 특정 상태)를 만든다. 증상만 없애는 임시방편(예: 에러를 무시하는 try/catch 추가)이 아니라 근본 원인을 고친다.

### 7. 수정

원인이 있는 계층에서만 수정한다. UI 버그를 domain 코드 수정으로 "우회"하지 않는다. 수정 범위는 원인에 대응하는 최소한으로 유지한다 — 관련 없는 리팩터링을 함께 하지 않는다.

### 8~10. 검증

```
dart format .
flutter analyze
flutter test
```

수정한 버그와 관련된 기존 테스트가 있으면 통과하는지 확인하고, 없다면 재발 방지를 위한 테스트를 추가하는 것을 고려한다. 검증 없이 "고쳤다"고 보고하지 않는다.
