# UI Information Architecture

> `ui-principles.md`를 화면 구조로 구체화한다. 아직 실제 화면을 구현하지 않는다 — 이 문서는 Phase 3+ 구현 시 따를 화면 트리와 이동 구조를 정의한다. Auth 관련 화면/흐름은 Phase 2에서 이미 구현이 끝난 실제 구조를 그대로 반영한다(`docs/architecture/architecture.md` "실제 구현된 구조(v7)" 참고).

## Senior 전체 화면 구조

```
[Auth 흐름 — 구현 완료, Phase 2]
전화번호 입력 → OTP 확인 → PIN 설정(신규) / PIN 확인(기존) → 역할 선택(최초 1회) → 홈

[홈 — 하단 네비게이션 진입점]
├─ 정보(info)
│   ├─ 맞춤 정보 카드(나이 기반 — 기초연금/건강검진/보이스피싱 등)
│   └─ 근처 경로당/복지센터 리스트 → 상세(설명+신청방법+외부링크+전화)
│
├─ 홈(home) — 기본 진입 탭
│   ├─ 핵심 기능 3~5개: 문서 촬영 / 문자 확인 / 경로당 찾기 / 음성 비서 / 긴급 도움
│   ├─ 오늘 해야 할 일 요약(→ 일정 전체 보기)
│   └─ 긴급 도움 플로팅 버튼(상시 노출) → 모달(보호자/119/112/118)
│
├─ 기록(analysis + schedule)
│   ├─ 분석 기록 리스트(Empty State 대응) → 상세(원문/요약/신뢰도/위험배지)
│   └─ 일정 리스트(Empty State 대응)
│
└─ 더보기(profile 진입점)
    ├─ 내 정보(profile 수정)
    ├─ 연결된 보호자 목록(신규 확정 — 다중 보호자 관리/해제)
    ├─ 통계(고지서 통계 — 어르신 쪽에서는 요약만, 상세 통계는 보호자 앱 담당)
    ├─ 알아두면 좋은 정보
    ├─ 사용 방법 안내(튜토리얼 재실행)
    ├─ 설정(settings)
    │   ├─ 접근성(글자크기/음성속도/음성안내/언어)
    │   ├─ 쉬운 모드 토글
    │   ├─ 계정(마스킹된 전화번호)/로그아웃/회원 탈퇴
    │   ├─ 보호자 알림 설정("위험 문자 발견 시 보호자에게 알릴지", 기본 꺼짐)
    │   └─ **개인정보 공개 범위 안내(신규)**: "보호자에게는 문자 원문이 아니라 요약만 전달돼요" 같은 명시적 고지 — `ui-principles.md` Guardian 5 근거
    └─ 고객 지원(support)
        ├─ 사용 방법 안내 / 화면 안내 다시 보기
        ├─ 고객센터 연결
        └─ 개인정보는 어떻게 보관되나요?

[기능별 상세 흐름]
document_scan: 홈/기록 → 촬영 화면(프레임 가이드+안정 시 자동 촬영+수동 촬영 버튼+플래시 상태 표시) → 분석 중(AppLoading 중요작업 variant) → 결과(신뢰도 먼저 표시 → 원문/요약)
message_check: 홈 → 문자 선택/붙여넣기(Android는 리스트에서 선택, 그 외 플랫폼은 대체 입력) → 분석 중 → 결과(신뢰도+위험배지+요약+주의사유+확인할일)
voice_assistant: 홈(마이크 버튼, 긴급 도움과 시각적으로 구분되는 색상) → 듣는 중(파형+텍스트) → 처리 중(AppLoading 중요작업) → 답변(텍스트+TTS+다시듣기) — 기존 화면 기능으로 결과를 이어받을 수 있어야 함(원칙 9)
emergency_help: 상시 플로팅 버튼 → 모달(보호자 전화/119/112/118/사용법 다시보기)
welfare_center: 정보 탭 내 리스트/상세, 위치 권한 거부 시 주소 직접 입력 폴백
connection: 더보기 → 연결된 보호자 목록 → 개별 해제 / 신규 연결 요청 수락(요청이 오면 알림)
```

### Easy Mode에서의 구조 차이

- 하단 네비게이션은 유지하되, 홈 탭에 핵심 5기능(문서/문자/경로당/음성비서/긴급도움)만 큰 카드로 노출하고 나머지(정보 카드, 통계 요약 등)는 "더보기"로 이동.
- "기록" 탭 진입 없이도 홈에서 "오늘 해야 할 일"이 바로 보이게(탭 깊이 최소화).
- 상세 화면 진입 시에도 항상 "← 홈으로" 텍스트 링크로 1탭 복귀 가능하게 유지.

## Guardian 전체 화면 구조

```
[Auth 흐름 — 구현 완료, Phase 2]
전화번호 입력 → OTP 확인 → PIN 설정(신규) / PIN 확인(기존) → 역할 선택(최초 1회) → 어르신 연결 여부에 따라:
  ├─ 연결된 어르신 없음 → AppEmptyState("아직 연결된 어르신이 없습니다" + "어르신 연결하기" Action)
  └─ 연결됨 → 홈

[홈 — 하단 네비게이션 진입점]
├─ 홈(home) — "지금 우리 어르신 괜찮으신가"에 답하는 요약이 최상단
│   ├─ 어르신 프로필 카드(이름/나이/지역 요약) + 전화 버튼
│   ├─ 오늘의 안심 상태 배너(위험 있음/없음 — 3단계 중 가장 심각한 것 기준)
│   ├─ 최근 활동 요약(3~5개, 위험도순 정렬 우선)
│   └─ 다가오는 일정 요약
│
├─ 알림(notification, 기존 "받은 연락"에서 명명 정리)
│   └─ 위험/일반 알림 리스트(안읽음 배지) → 상세(원문 대신 요약/위험배지/주의이유/확인할일)
│
├─ 기록(analysis + schedule)
│   └─ 어르신이 확인한 문서/문자 이력, 필터(전체/위험/문서/문자) — 점진적 노출(리스트→상세)
│
├─ 통계(statistics)
│   └─ 이번 달 분석 수 / 위험 문자 수 / 일정 완료·잔여 / 고지서 추세(선그래프 1개 + 요약 문장, 다중 차트 지양)
│
└─ 더보기(profile 진입점)
    ├─ 어르신 앱 열기 안내(**확정**: Deep Link/App Link 확장 가능성만 남기고 이번 Phase에서는 구현하지 않음 — 아래 "Guardian → Senior 전환" 참고)
    ├─ 다른 어르신 연결(1:N — §"Guardian 1:N 어르신 선택 구조" 참고)
    ├─ 위험 알림 설정(즉시 푸시 on/off)
    ├─ 연결 해제
    └─ 고객 지원(support)
```

### Guardian → Senior 전환 (확정, Decision 1)

기존 앱의 "어르신용 앱 열기(별도 인증 전환 없이 페이지만 전환)" 패턴은 **채택하지 않는다.** Senior App과 Guardian App은 완전히 독립된 Flutter 앱(별도 인증 세션)이라는 Architecture 결정을 UI에서도 그대로 지킨다.

- Guardian App의 인증 상태를 Senior App 인증으로 사용하지 않는다.
- Guardian App이 Senior App의 내부 화면을 직접 제어하지 않는다.
- Senior App은 자체 Session + PIN Gate 정책(Phase 2 구현)을 독립적으로 적용한다 — Guardian에서 넘어온 진입이라고 해서 PIN Gate를 건너뛰지 않는다.
- 향후 필요해지면 **Deep Link/App Link**로 Senior App을 "여는" 정도까지만 확장 가능성을 열어둔다(예: 앱이 이미 설치되어 있으면 Senior App이 자체 인증 흐름을 그대로 거쳐 실행됨). **이번 Phase에서는 Deep Link 자체를 구현하지 않는다** — 더보기 메뉴의 "어르신 앱 안내" 항목도 실제 전환 기능 없이 정적 안내(설치 여부 안내 등)로만 존재하거나, Phase 3에서는 아예 노출하지 않을 수 있다(화면 구현 시 확정).

### Guardian 1:N 어르신 선택 구조 (확정, Decision 2)

Guardian App은 최초 구현부터 1:N(다중 어르신)을 기본 Architecture로 고려한다. 단, 복잡한 관리 기능(어르신별 권한 세분화 등)은 처음부터 만들지 않는다.

```
Guardian Home
  → 현재 선택된 어르신(selectedElderId)
  → 어르신별 데이터 표시
```

- **어르신이 1명인 경우**: 선택 UI를 최소화한다(스위처를 아예 숨기거나, 이름만 조용히 표시).
- **어르신이 2명 이상인 경우**: 어르신 선택 UI를 제공한다. Dropdown 또는 Bottom Sheet 형태를 우선 검토(최종 형태는 Phase 3 구현 시 화면 밀도를 보고 결정).
- 선택된 `elder_id` 기준으로 아래 전부를 조회한다: 안심 상태, 받은 연락(알림), 기록, 통계, 위험 알림.
- 현재 선택된 어르신이 누구인지 화면 어디서든(홈뿐 아니라 알림/기록/통계 탭에서도) 항상 명확히 표시한다 — 탭을 이동해도 선택 상태가 유지된다.
- 이 구조는 `guardian_links`의 기존 N:M 스키마(§1-5)와 충돌하지 않는다 — `elder_id`는 이미 존재하는 컬럼을 그대로 selector로 사용하는 것뿐이다.

### 정보 공개 경계(모든 화면에 걸친 규칙)

보호자 화면 어디에도 문자/문서 원문 전체를 그대로 노출하지 않는다. 노출 가능 필드는 `technical-decisions.md` §2-4 화이트리스트를 따르고, 이 경계를 화면에도 은연중이 아니라 명시적으로 안내한다(예: 알림 상세 화면 하단에 "원문은 어르신 개인정보로 보호돼요" 같은 짧은 안내).

## 화면 이동 구조 요약

- **Senior**: 하단 탭 4개(정보/홈/기록/더보기) + 상시 플로팅 긴급 버튼. 상세 화면은 텍스트 링크로 복귀. 기능형 화면(document_scan/message_check/voice_assistant)은 탭에서 진입해 모달/풀스크린으로 확장 후 결과에서 홈 또는 기록으로 복귀.
- **Guardian**: 하단 탭 5개(홈/알림/기록/통계/더보기) — 구현 시 기존 온담앱 관찰(`user-flow.md` "5. 보호자용 온담")과 일관되게 더보기를 별도 진입점이 아니라 5번째 탭으로 두었다. 알림 상세 → 기록 상세는 동일 데이터를 가리키므로 상호 링크(알림에서 "기록에서 보기", 기록에서 해당 알림 배지 표시). 어르신이 2명 이상이면 선택된 어르신 표시(스위처)가 홈 탭 상단에 노출된다.
- 두 앱 모두 라우터는 독립적으로 구현되어 있으며(Phase 2 `app/router/`), 위 구조는 Phase 3+에서 각 앱의 `app_router.dart`에 실제 라우트로 추가한다.

## 주요 사용자 흐름

### Senior: 위험 문자 발견 → 보호자 알림
```
홈 → 문자 확인 → 분석 중 → 결과(신뢰도 먼저, 위험배지 표시)
  → "보호자에게 알리기" 버튼(옵트인, 설정에서 기본 꺼짐이어도 개별 건은 매번 선택 가능)
  → 확인 다이얼로그(비용이 큰 행동 — 원칙 7) → 전송
```

### Senior: 문서 촬영 → 분석
```
홈/기록 → 문서 촬영 → 카메라(프레임 가이드, 플래시 상태 항상 표시, 안정 시 자동 촬영 + 수동 버튼)
  → 원본 즉시 삭제 대상 안내(이미 확정된 정책) → 분석 중 → 결과(신뢰도 → 요약 → 원문 스캔 이미지는 결과 화면에서만 임시 열람)
```

### Guardian: 위험 알림 수신 → 확인
```
Push 수신(위험만 즉시) → 앱 열기 → 홈(안심 상태 배너에 이미 반영) → 알림 탭 → 상세(요약/위험배지/주의이유/확인할일)
  → "기록에서 보기"(선택) → 어르신에게 전화(선택)
```

### Senior: 보호자 연결 QR 표시 (v9 신규)
```
더보기/홈 → 보호자 연결 → QR 코드 표시("보호자에게 이 QR을 보여주세요")
  → (보호자가 스캔) → 연결 요청 알림 수신 → 확인 → 수락/거절
```

### Guardian: 신규 연결 — QR 스캔 (v9: 전화번호/연결코드 입력 → QR 스캔으로 갱신)
```
더보기 → 어르신 연결하기 → QR 코드 스캔(카메라 권한 필요) → 요청 생성(pending)
  → (Senior 쪽) 연결 요청 알림 → 확인 → 수락 → (Guardian 쪽) 홈이 AppEmptyState에서 실제 데이터로 전환
```
- 카메라 권한 거부 시 명확한 안내 + 재시도/설정 이동 제공.
- QR 스캔 성공은 요청 생성일 뿐 연결 완료가 아니다 — 어르신 수락 후에만 Guardian 홈이 실데이터로 전환된다.

## 결정 완료 (사용자 확정, Phase 3 착수 전)

1. **"어르신용 앱 열기"** — 채택하지 않음. Deep Link/App Link로 확장 가능성만 남기고 이번 Phase에서는 구현하지 않는다. 상세는 위 "Guardian → Senior 전환" 참고.
2. **Guardian 1:N(다중 어르신) UI 시점** — 최초 구현부터 기본 Architecture로 고려한다(단, 복잡한 관리 기능은 제외). 상세는 위 "Guardian 1:N 어르신 선택 구조" 참고.
3. **고지서 통계 차트 라이브러리** — 지금 확정하지 않는다. Phase 6에서 실제 `structuredFields` 데이터와 통계 요구사항이 확정된 뒤 결정한다. 지금은 `AppStatCard` + 추세 문장 + 차트를 담을 컴포넌트 구조만 고려하고, 특정 차트 라이브러리를 `pubspec.yaml`에 추가하지 않는다(`ui-component-spec.md` AppStatCard 절 참고).
