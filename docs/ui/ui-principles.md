# UI Principles — ONDAM UX 원칙

> `ui-research.md`의 조사 결과를 그대로 복사하지 않고, ONDAM에 맞게 재정의한 원칙이다. Phase 3 이후 모든 화면 설계·컴포넌트 설계는 이 원칙을 기준으로 판단한다. 원칙과 실제 화면 구조의 연결은 `ui-information-architecture.md`, 화면별 적용은 `ui-screen-spec.md` 참고.

---

## Senior App UX 원칙

### 1. 고령층 우선 (Universal Design, not "시니어 모드")
쉬운 모드를 "나이 든 사람을 위한 특수 모드"로 취급하지 않는다. Toss 리서치가 보여주듯 접근성 좋은 설계는 예외 케이스 처리가 아니라 기본 설계 품질의 문제다. **쉬운 모드가 잘 만들어졌다면, 그 설계는 일반 모드에도 좋은 설계다.** 판단 기준: "이 화면이 일반 모드에서도 이렇게 단순했다면 더 나았을까?"를 항상 자문한다.

### 2. 한 화면 한 목적
화면 하나는 하나의 결정/행동만 요구한다. 여러 목적이 섞인 화면(예: 정보 확인 + 설정 변경 + 다음 단계 선택이 한 화면에)은 분리한다. GrandPad의 "90/90 보증"처럼, 화면에 들어서면 무엇을 하면 되는지 즉시 알 수 있어야 한다.

### 3. 큰 터치 영역
- 일반 모드: 최소 48dp(Material 기준), 권장 56dp.
- 쉬운 모드: 최소 56dp, 권장 64~76dp(PIN 키패드가 이미 이 기준 — Senior 76px).
- 터치 영역 간 최소 8dp 간격을 항상 유지한다(오터치 방지).
- 이 값들은 `AppSpacing`/컴포넌트 자체 크기로 강제한다 — 화면별로 임의 크기를 쓰지 않는다.

### 4. 짧고 명확한 문장
한 문장에 하나의 정보만 담는다. 전문 용어·약어·수동태를 피한다. "신뢰도"는 절대 숫자/퍼센트로 말하지 않고 "높음/보통/낮음" 또는 문장형("이 답변은 비교적 확실해요")으로만 표현한다(`ui-research.md` 9번). 오류는 항상 "무슨 일이 있었는지 + 다음에 뭘 하면 되는지" 두 부분으로 구성한다(원칙 7과 연결).

### 5. 복잡한 선택 최소화
한 화면에서 요구하는 선택지는 최대한 줄인다. 선택지가 3개를 넘으면 우선순위를 재검토하거나 단계를 나눈다. 설정 화면에서도 "지금 당장 필요한 선택"과 "나중에 바꿔도 되는 선택"을 구분해, 온보딩에서는 전자만 묻는다(기존 KEEP-2 온보딩 순서와 일치).

### 6. 위험 정보는 명확하게 구분
위험(위험 문자 감지 등)은 **색상 + 아이콘 + 텍스트 배지** 3중 표현을 항상 함께 쓴다(색상 단독 금지 — 기존 ui-spec.md 원칙 유지). 위험 색상(`AppColors.error`/향후 `emergency` 토큰 계열)은 신뢰도 표시나 일반 경고에 재사용하지 않는다(`ui-research.md` 9·Guardian 7 — 위험도 색상과 신뢰도 색상은 서로 다른 토큰 계열).

### 7. 실패했을 때 다음 행동을 알려주는 UX
모든 에러/실패 상태는 "무엇이 잘못됐는지"만이 아니라 "지금 무엇을 하면 되는지"까지 반드시 포함한다(재시도 버튼, 대체 경로, 문의 안내 등). 빈 화면이나 조용한 실패를 만들지 않는다(`ui-research.md` 10, GOV.UK 오류 요약 패턴). 이 원칙은 이미 Phase 2 PIN 오류 UX(`PIN이 올바르지 않아요. (3회 실패)`)에 반영되어 있다 — 앞으로 모든 화면에 동일하게 적용한다.

### 8. 쉬운 모드를 앱 전체의 핵심 UX로 사용
쉬운 모드는 설정 안의 토글이 아니라 앱을 처음 여는 사용자가 마주하는 기본 경험에 가깝게 설계한다. 상세는 아래 "Easy Mode 원칙" 참고.

### 9. 음성 비서와 기존 기능이 자연스럽게 연결되는 구조
음성 비서는 별도의 "새 기능"이 아니라 기존 화면 조작(문서 촬영, 문자 확인, 경로당 찾기, 일정 확인)의 **대체 입력 경로**로 설계한다. 음성으로 시작한 작업이 화면 조작으로 이어받아지거나, 화면에서 하던 작업을 음성으로 재개할 수 있어야 한다(단방향 "명령→결과"로 끝나지 않음). 확인(confirmation)은 되돌리기 어렵거나 보호자에게 영향이 가는 행동에만 요구하고, 단순 조회/이동에는 매번 확인받지 않는다(`ui-research.md` 7).

## Guardian App UX 원칙

### 1. 빠른 상황 파악
보호자 홈은 무엇보다 먼저 "지금 우리 어르신은 괜찮으신가"에 한 문장/한 카드로 답해야 한다. 원시 이벤트 목록으로 시작하지 않는다(Life360 비평 — `ui-research.md` Guardian 1).

### 2. 중요한 위험 정보 우선
정렬 기준은 시간순이 아니라 **위험도순**이다. 홈 화면 정보량은 3~5개 핵심 항목으로 제한한다(`ui-research.md` Guardian 4, 5).

### 3. 상세 정보는 단계적으로 노출
홈은 요약만, 상세(원문 분석 결과, 전체 기록)는 탭해서 들어가는 점진적 노출(progressive disclosure) 구조를 따른다. 요약과 상세는 서로 다른 조회(Repository/UseCase 레벨에서도 분리 가능)로 다뤄 로딩 속도와 화면 밀도를 함께 관리한다(`ui-research.md` Guardian 7).

### 4. 통계는 과도하게 복잡하지 않게
고지서 통계는 "추세를 설명하는 한 문장 + 단순 차트 1개"를 기본형으로 한다. 파이차트를 다용도로 남발하지 않고, 용도별로 차트 유형을 고정한다(추세=선그래프, 카테고리 비교=막대, 한도 대비=진행바)(`ui-research.md` Guardian 5).

### 5. 어르신 개인정보 최소 노출
보호자에게 노출 가능한 필드는 이미 확정된 화이트리스트(`technical-decisions.md` §2-4)를 그대로 따른다. 원문이 아니라 구조화된 요약만 보여준다. **이 경계는 서버 정책으로만 끝내지 않고, Senior 앱 쪽 화면에도 "어떤 정보가 보호자에게 전달되는지/전달되지 않는지"를 명시적으로 노출**한다(`ui-research.md` Guardian 6 — Google Family Link의 양방향 공개 패턴, 현재 설계의 공백으로 확인됨).

### 6. 알림과 기록의 관계를 명확하게 표시
푸시로 온 위험 알림과 분석 기록 리스트의 항목이 같은 데이터라는 것을 UI에서 분명히 연결한다(알림 탭 → 해당 기록 상세로 바로 이동). 같은 사건에 대해 중복 알림을 보내지 않는다(`ui-research.md` Guardian 4, Apple HIG). 알림 심각도는 표시상 3단계(고/중/저)로 구분하되, 실제 푸시 발송 여부는 위험(즉시 발송) vs 그 외(인앱/다이제스트)의 2단계로 단순화한다.

## Easy Mode 원칙

> "글자와 버튼을 크게" 만드는 기능이 아니라 Senior App의 핵심 UX 전략이다. 상세 설계는 `ui-information-architecture.md`의 Easy Mode 절, Normal/Easy 차이표 참고.

1. **정보 밀도**: 한 화면의 카드/버튼 수를 Normal Mode 대비 눈에 띄게 줄인다(핵심 기능만: 문서 촬영/문자 확인/경로당 찾기/음성 비서/긴급 도움).
2. **문장 길이**: 한 문장, 한 개념. 부제·설명은 꼭 필요한 경우에만 1줄 추가.
3. **아이콘 + 텍스트 조합을 항상 함께**: 아이콘 단독으로 의미를 전달하지 않는다(카메라 플래시 상태 표시 원칙과 동일 — `ui-spec.md` 기존 결정 유지).
4. **화면 이동 깊이 최소화**: 핵심 기능까지 탭 1~2회(기존 `ui-spec.md` 결정 유지). GrandPad의 "평평한 네비게이션" 원칙 적용.
5. **음성 안내**: 접근성 설정(음성 안내 on/off, 속도)과는 독립적으로, 쉬운 모드 진입/주요 화면 전환 시 보조적 음성 피드백을 제공할지는 Phase 3+ 구현 시점에 결정(설계만 열어둠 — 강제하지 않음).
6. **오류 메시지**: Easy Mode에서는 Normal Mode보다 문장을 더 짧게, 다음 행동을 더 단순하게(선택지 1개로) 줄인다.
7. **확인/취소 구조**: 되돌릴 수 없는 행동(계정 탈퇴, 보호자 연결 해제 등)만 확인 다이얼로그를 띄우고, 그 외에는 즉시 실행 후 취소 가능하게(Undo) 하는 것을 Normal Mode보다 더 적극적으로 검토한다 — 다이얼로그 자체가 고령 사용자에게 추가 인지 부담이 될 수 있기 때문(단, 이 절충은 Phase 3+ 화면 설계 시점에 화면별로 재검토).
8. **화면 이동 깊이**: 뒤로가기는 항상 텍스트+화살표 형태로 명확히 표시(기존 `ui-spec.md` "← 홈으로" 패턴 유지), 제스처만으로 뒤로가기를 요구하지 않는다.

### Normal Mode vs Easy Mode 차이 요약

| 항목 | Normal Mode | Easy Mode |
|---|---|---|
| 홈 카드/버튼 수 | 제한 없음(정보 카드 포함 다수) | 핵심 5개 이하 |
| 버튼 최소 크기 | 48dp | 56~76dp |
| 텍스트 스타일 | `AppTextStyles` 기본 스케일 | 기본 스케일에 확대 배수 적용(정확한 배수는 `ui-component-spec.md`에서 정의) |
| 하단 네비게이션 | 탭 4~5개, 텍스트+아이콘 | 탭 수 축소 검토 또는 동일 탭에 라벨 강조 |
| 정보 카드(나이 기반 맞춤 정보 등) | 노출 | 홈에서는 축소, "더보기"로 이동 |
| 확인 다이얼로그 | 표준 사용 | 되돌릴 수 없는 행동에만 사용 |
| 화면 이동 깊이(핵심 기능 기준) | 제한 없음 | 최대 1~2탭 |

## Accessibility 원칙

1. **터치 영역**: 일반 48dp / 쉬운 모드 56~76dp, 요소 간 최소 8dp 간격(`ui-research.md` 8).
2. **색상 대비**: 본문 텍스트 4.5:1, 큰 텍스트 3:1, 비텍스트 컴포넌트(버튼/아이콘) 3:1 이상. `AppColors` 신규/변경 시 라이트·다크 양쪽에서 검증.
3. **색상 단독 의존 금지**: 위험/경고/성공 등 상태는 항상 색상+아이콘+텍스트 3중으로 표현.
4. **텍스트 확대 대응**: 레이아웃이 200% 확대까지 깨지지 않아야 한다 — 고정 높이 컨테이너에 텍스트를 강제로 맞추지 않는다(`flutter.md`/`ui-design.md` 기존 규칙과 일치, 리서치로 재확인).
5. **스크롤 어포던스**: 큰글씨 모드에서 리스트가 길어져 스크롤이 필요해지는 경우, 잘림이 안 보이지 않도록 시각적 신호(그라데이션 페이드, "더 보기" 표시 등)를 제공한다(Toss 사례 — `ui-research.md` 1).
6. **의미 전달**: 아이콘 버튼에는 `Semantics`/`tooltip`으로 스크린리더가 읽을 수 있는 설명을 제공(기존 `ui-design.md` 규칙 유지).

## Error / Loading / Empty UX 원칙

- **Loading**: 단순 데이터 로딩은 `AppLoading` 기본형(스피너만), 중요 작업(문서 분석, PIN 검증 등)은 "지금 무슨 일이 일어나고 있는지" 설명 텍스트 + 스피너 병행(기존 `ui-spec.md` 결정 A 유지, 리서치로 추가 근거 없음 — 기존 결정을 바꾸지 않음).
- **Error**: "무엇이 잘못됐는지 + 다음에 뭘 하면 되는지"를 항상 함께. 재시도 가능한 오류는 재시도 버튼을 명확히 제공(`AppError` 기존 패턴 유지, 강화 근거는 `ui-research.md` 10, GOV.UK 오류 요약 패턴).
- **Empty**: 공통 `AppEmptyState` 유지(기존 결정) — "무엇이 없는지 + 어떻게 채울 수 있는지" 2줄 구조.
- **Confirmation**: 되돌리기 어렵거나 비용이 큰 행동에만 확인을 요구한다(계정 탈퇴, 보호자 연결 해제, 음성 비서를 통한 보호자 알림 발송 등). 단순 조회/이동에는 확인을 요구하지 않는다(`ui-research.md` Senior 7 — Google Conversation Design 원칙, Voice에 국한되지 않고 전체 UI에 적용).
