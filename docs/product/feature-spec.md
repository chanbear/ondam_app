# 기능 명세

> `current-app-analysis.md`의 관찰 결과를 KEEP/MODIFY/REMOVE/ADD로 분류한다.
> 사용자가 직접 결정하지 않은 REMOVE/ADD 항목은 `PROPOSED`로 표시하며, 사용자 확인 전까지 확정 사항으로 간주하지 않는다.
>
> **개정 이력**: `docs/architecture/technical-decisions.md` v2에서 Architecture 결정 11개 + UI 결정 5개가 확정되면서, 아래 REMOVE/ADD 중 상당수가 `PROPOSED`에서 **확정**으로 전환되었다. 남은 `PROPOSED` 항목만 여전히 사용자 확인 대기 중이다.

## KEEP

기존 앱에서 그대로 또는 거의 동일하게 재구현할 가치가 있다고 판단한 기능.

1. **전화번호 + PIN 로그인 흐름 유지, 단 가입 시 OTP 1회 검증 추가** *(technical-decisions.md §1-3로 세부 확정)* — 평상시 로그인은 기존과 동일하게 전화번호+PIN(어르신 접근성 고려, 매번 OTP 요구 안 함), 가입 시에는 전화번호 소유 확인을 위한 OTP를 추가.
2. **온보딩 - 접근성 설정 우선(글자크기/음성속도/음성안내/언어)** — 기능 사용 전에 접근성부터 맞추는 순서가 타깃 사용자에 적합.
3. **쉬운 모드(대형 버튼 UI 전환)** — 가장 핵심적인 차별화 요소. `technical-decisions.md` UI 결정 A로 상세 확정(전체 앱 적용, 버튼/정보량/Navigation/화면복잡도/텍스트/여백/기능우선순위까지 변경되는 별도 UX 모드).
4. **홈의 3대 핵심 기능(문서 촬영 / 문자 내용 요약 / 경로당·복지센터 찾기)** — 앱 정체성과 직결되는 핵심 기능.
5. **각 기능별 "사용 방법 보기" 링크 + 단계별 튜토리얼 오버레이** — 고령층 대상 온보딩 보조 장치로 유효.
6. **긴급 도움 플로팅 버튼(보호자/119/112/118 연결)** — 상시 노출되는 안전 기능, 최우선 유지.
7. **나이 기반 맞춤 정보 카드(기초연금/건강검진/보이스피싱 등)** — 개인화된 실질적 도움 정보.
8. **위치 기반 + 주소 텍스트 검색 폴백을 모두 지원하는 경로당/복지센터 찾기** — 위치 권한을 거부해도 사용 가능한 대안 제공.
9. **분석 기록/일정/고지서 통계의 명확한 Empty State 문구** — 빈 상태에서도 다음 행동을 안내. `technical-decisions.md` UI 결정 C로 공통 `AppEmptyState` 컴포넌트화가 확정.
10. **보호자 앱의 "안심 상태 요약 + 받은 연락 + 분석 기록 + 안심 통계" 4분할 구조** — 보호자가 한눈에 상태를 파악하는 정보 구조는 유효.
11. **위험 문자 감지 시 보호자에게 알릴지 여부를 어르신이 직접 선택(옵트인, 기본 꺼짐)** — 자기결정권을 존중하는 기본값 설계. 전달 메커니즘은 Push+서버 저장으로 확정(MODIFY-4 참고).
12. **보호자 연결 시 어르신 개인정보(비밀번호 등)는 전달되지 않는다는 원칙** — `technical-decisions.md` §1-5 필수요구사항("연결된 보호자에게는 필요한 최소 정보만 제공")과 §2-4(개인정보 접근 범위 화이트리스트)로 구체화.
13. **보호자 앱 "받은 연락" 상세의 원문/요약/주의 이유/확인할 일 구조화된 정보 제공 방식**.

## MODIFY

기능은 필요하지만 동작·UX·구조를 개선해야 하는 항목.

1. **로그인 - 비밀번호 자릿수 제약 사전 안내**: "4자리 숫자"라는 제약을 입력 필드 placeholder/hint에 미리 노출해 제출 후 에러로 알게 되는 현재 흐름을 개선.
2. **관리자 테스트 로그인**: 현재 완전히 비활성 상태. 실제 필요 여부는 REMOVE(PROPOSED)-2 참고(아직 사용자 확인 전).
3. **위치 기반 경로당 찾기 실패 처리**: 권한 거부/네트워크 오류/결과 없음을 구분해 사용자에게 다른 다음 행동을 안내하도록 개선.
4. **보호자 알림 메커니즘 — 확정: Push(FCM) + 서버 저장 방식으로 통일** *(기존 "권장"에서 확정으로 승격, `technical-decisions.md` §1-4)*: 기존 앱의 "SMS 앱을 열어 수동 발송" 문구/흐름은 신규 앱에서 사용하지 않는다. SMS는 향후 앱 미설치/Push 미수신 시 보조 채널로만 확장 가능하도록 구조를 열어둔다(즉시 구현 대상 아님).
5. **온보딩 개인정보 입력 폼의 포커스/입력 안정성**: 필드 간 입력이 누락되는 현상이 관찰됨 — 재구현 시 폼 상태 관리를 견고하게 설계.
6. **보호자-어르신 연결 인증 — 확정: 어르신 수락(승인) 방식** *(기존 "검토"에서 확정으로 승격, `technical-decisions.md` §1-6)*: 보호자가 어르신 전화번호(또는 연결 코드)를 입력하면 `pending` 상태의 연결 요청이 생성되고, 어르신이 앱에서 직접 확인 후 수락해야 연결이 완료된다. 전화번호만으로 즉시 연결되는 기존 방식은 사용하지 않는다.
7. **문자 내용 요약 기능의 플랫폼 제약 안내**: "안드로이드 전용" 기능임을 처음부터 명확히 하고, iOS 등 지원 불가 환경에서의 대안 UX(붙여넣기/공유/직접입력/기능제한)를 확정된 방향(`technical-decisions.md` §1-9)에 따라 구현.
8. **인증에 OTP 검증 추가 — 확정**: 가입 시 전화번호+OTP+PIN 3단계, 평상시 로그인은 전화번호+PIN만(MODIFY 상세는 KEEP-1과 연결). 실제 Supabase Auth 결합 방식은 `technical-decisions.md` OPEN QUESTIONS 1번에서 구현 착수 시 확정.
9. **"일정"을 분석 기록에서 분리해 독립 도메인(`schedule` feature)으로 취급 — 확정**: 어르신 기록 탭의 일정과 보호자 앱의 "다가오는 일정"이 같은 원천 데이터의 다른 뷰라는 점이 재검토로 확인됨. `implementation-plan.md` §1 feature 구조에 반영됨.

## REMOVE

### 확정

1. **보호자 앱의 Mock 데이터 기반 "연결 전 화면 미리보기" 전체** *(`technical-decisions.md` UI 결정 E로 확정)*: 프로덕션에서는 사용하지 않는다. 연결 전 상태는 `AppEmptyState`로 "아직 연결된 어르신이 없습니다 → 어르신 연결하기" 형태로 대체한다.
2. **보호자 앱의 "새 위험 연락 테스트" / "테스트 자료 다시 채우기" 데모 전용 메뉴** *(위 1번 결정에 따라 자연히 확정)*: Mock 프리뷰 자체를 없애므로 이를 조작하는 데모 도구도 함께 제거.

### (PROPOSED) — 사용자 확인 전

3. **(PROPOSED) 네이버 로그인 버튼 (현재 "곧 지원 예정" 상태)**: 실제 지원 전까지 비활성 버튼을 노출하는 것은 혼란을 줄 수 있음. 실제 출시 시점에 맞춰 노출하는 방향 제안.
4. **(PROPOSED) "관리자 테스트 로그인" 버튼**: 프로덕션 사용자 화면에 노출된 개발/QA용으로 추정되는 버튼. 최종 앱에는 노출하지 않는 방향 제안(내부 QA 빌드에만 존재).

## ADD

### 확정

1. **어르신 측에서 등록된 보호자 목록을 확인하고 연결을 해제하는 메뉴** *(`technical-decisions.md` §1-5 필수요구사항으로 확정)*: 보호자 쪽 "연결 해제"만 있던 기존 앱과 달리, 신규 앱은 어르신도 자신의 보호자 목록 조회/해제가 가능해야 한다.
2. **어르신-보호자 연결 요청/수락 플로우** *(§1-6 확정)*: 보호자가 요청을 보내면 어르신이 앱에서 확인 후 수락하는 절차. 필요 시 추가 OTP/연결 코드를 나중에 붙일 수 있도록 확장 가능하게 설계(최초 구현 필수 요소는 아님).
3. **어르신 측 다중 보호자 등록 UI** *(§1-5, 1:N 기본으로 확정)*: 어르신 1명에게 보호자가 여러 명 연결될 수 있으므로, 보호자 목록을 리스트 형태로 보여주고 각각 관리(해제 등)할 수 있는 UI가 필요.
4. **실제 Push 알림 인프라(FCM)** *(§1-4, §1-10 확정)*: 5개 분석 문서 어디에도 없던 공백이었으나, "위험 알림" 토글이 실제로 동작하려면 필수. `features/notification`으로 구현.

### (PROPOSED) — 사용자 확인 전

5. **(PROPOSED) 위치 조회 실패 시 원인별 안내 메시지**(권한 거부 안내 + 설정으로 이동 유도 등) — 이번 Architecture 결정 범위 밖이라 여전히 PROPOSED.

## ADD / NEW (신규 요구사항, 이번 라운드 추가)

> 사용자가 이번에 새로 요청한 6개 기능. 1~5는 방향이 확정된 신규 요구사항이며, 6(관리자 시스템)만 `PROPOSED`다. 세부 Architecture는 `docs/architecture/architecture.md`, 기술 미결정 사항은 `docs/architecture/technical-decisions.md` §5, Phase 배치는 `docs/product/implementation-plan.md`를 참고.

1. **음성 비서**: 어르신이 화면 조작 없이 음성으로 주요 기능(문서 촬영 안내, 문자 확인, 경로당 찾기, 일정 확인 등)을 이용할 수 있도록 지원. `음성 입력 → STT → 의도/질문 분석 → 온담 기능 또는 AI 처리 → 답변 → TTS 음성 출력` 구조로 확장 가능하게 설계(지금 단계에서는 구조만 설계, STT/TTS/AI 서비스는 미확정 — `technical-decisions.md` OPEN QUESTIONS 참고).
2. **쉬운 모드 Main 강화**: 기존에 KEEP-3으로 유지하기로 한 쉬운 모드를 "설정 옵션"이 아니라 **어르신용 앱의 핵심 Main UX**로 격상. 큰 버튼, 핵심 기능 중심 Navigation, 음성 비서, 긴급 도움, 직관적 안내가 하나의 경험으로 연결되도록 홈 화면을 재설계. 기존 `easyModeProvider` 설계는 유지.
3. **카메라 플래시 제어**: 문서/사진 촬영 시 플래시 ON/OFF/자동을 선택할 수 있는 기능. 어르신 사용자를 고려해 작은 아이콘만이 아니라 현재 상태가 명확히 보이고, 쉬운 모드에서는 큰 버튼으로 제공하며, 촬영 전 상태를 확인할 수 있어야 한다. `document_scan` feature의 촬영 화면에 포함(별도 feature 아님). Android/iOS 플랫폼 차이는 구현 Phase에서 확인.
4. **답변 신뢰도 알림**: AI/분석 결과 제공 시 결과의 확실성을 사용자가 이해할 수 있게 안내. AI의 내부 confidence score를 그대로 노출하지 않고, "높음/보통/낮음" 또는 "이 답변은 비교적 확실해요" 같은 사용자 친화적 표현으로 변환해 보여준다. 의료/법률/금융 등 고위험 판단이 아니라 **온담 AI 분석 결과 자체의 불확실성 안내**라는 원칙을 유지. `analysis` feature의 도메인 엔티티(`AnalysisResult`)에 신뢰도 메타데이터를 포함하고, `ui-spec.md`에 표현 규칙을 별도로 정의한다.
5. **보호자 앱 고지서 통계 동기화**: 어르신 앱의 고지서/문서 분석 결과를 구조화해 보호자 앱에서 통계로 보여주는 기능. 원본 문서를 그대로 노출하지 않고 필요한 통계만 표시(월별 고지서/금액 변화/주요 항목/기간 대비 변화/이상 변화/분석 건수 등으로 향후 확장 가능). 어떤 고지서 종류와 통계 항목을 최종 제공할지는 별도 Feature Spec에서 결정하며, 개인정보 최소화 원칙(§`technical-decisions.md` §1-5, §2-4)을 그대로 따른다.

### (PROPOSED) — 사용자 확인 전

6. **(PROPOSED) 관리자 시스템**: 사용자 관리, 보호자/어르신 연결 관리, 신고/오류 확인, 분석 처리 상태, AI 분석 로그, 서비스 통계, 공지사항/콘텐츠 관리, 시스템 상태, 테스트 계정 관리 등을 다루는 관리자 전용 앱/시스템. **지금 바로 구현하지 않으며, 실제 제품 범위 포함 여부도 아직 결정하지 않는다.** 일반 사용자용 어르신/보호자 앱에는 관리자 기능을 넣지 않는다. Architecture 상 확장 가능성만 열어둔다(`architecture.md` 참고).

## NEED DECISION → OPEN QUESTIONS로 이동

이전 버전의 "NEED DECISION" 항목은 `technical-decisions.md` v2에서 대부분 확정되었다. 남은 세부 구현 수준의 미결정 사항은 `docs/architecture/technical-decisions.md` §5 `OPEN QUESTIONS`를 참고한다(이 문서에서 중복 나열하지 않음).

## 확인 필요 (분류 보류, 변경 없음)

`current-app-analysis.md` 3장에 정리된 "확인 필요" 항목들은 이번 Architecture 결정과 무관하게 여전히 실제 동작 검증 전까지 KEEP/MODIFY/REMOVE/ADD 어느 쪽으로도 확정하지 않는다:

- 문서 촬영 실제 업로드·분석 결과 UI/플로우
- 긴급 연결 버튼의 실제 통화 연결 동작
- 소셜 로그인 실동작 여부
- "주변 복지센터·주민센터" 결과 공백 원인
