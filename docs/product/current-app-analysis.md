# 기존 온담앱 분석

> `app-analysis` skill workflow에 따라 작성. 분석 대상: 실제 배포된 웹앱
> - 어르신용: https://ondam-web.pages.dev/
> - 보호자용: https://ondam-web.pages.dev/guardian
>
> 분석 방법: Chrome 브라우저로 두 앱에 실제 회원가입 후 클릭/입력하며 탐색 (2026-08-12).
> 이 문서에 기록된 내용은 모두 브라우저에서 직접 관찰한 사실이다. 서버/DB 내부 구조, 실제 프로덕션 백엔드 존재 여부 등 화면만으로 확정할 수 없는 부분은 "확인 필요"로 별도 표기했다.

## 0. 분석 환경 관련 중요 전제

- 배포 형태: Cloudflare Pages 정적 호스팅(`*.pages.dev`)으로 추정. Flutter Web 빌드가 아니라 별도 웹 프레임워크(React 계열로 추정, class 기반 CSS)로 만들어진 **UX/기능 프로토타입**으로 보인다.
- 보호자 앱의 "다른 휴대폰 연결 안내" 팝업에 다음 문구가 명시되어 있다: **"현재 시제품은 같은 브라우저에 저장된 어르신 계정을 찾습니다. 실제 서비스에서는 서버에서 어르신 번호를 확인한 뒤 문자 인증 또는 어르신 승인을 추가할 수 있습니다."**
  → 즉 이 앱은 실제 백엔드 서버 없이 **브라우저 localStorage 기반으로 동작하는 클릭 프로토타입**임을 앱 스스로 인정하고 있다. 화면/플로우/문구는 요구사항 레퍼런스로 신뢰할 수 있지만, 실제 API/서버 아키텍처는 이 자료만으로 알 수 없다.
- 일부 기능("문자 내용 요약")은 "이 기능은 안드로이드 앱에서만 사용할 수 있어요"라는 안내와 함께 웹에서 동작하지 않는다. 즉 원래 타깃은 Android 네이티브(SMS 접근 등)이고, 웹은 그 외 기능의 데모/폴백이다.

## 2. 기능별 현재 동작 / 문제점

### 2-1. 로그인/인증

- 현재 동작: 전화번호 + 4자리 숫자 PIN. 계정 없으면 자동 생성(로그인=가입 통합). 구글 로그인 버튼 있으나 실동작 미검증. 네이버는 "곧 지원 예정" 문구로 버튼은 있지만 비활성 안내.
- 문제점: **"관리자 테스트 로그인" 버튼이 클릭해도 아무 반응이 없다**(콘솔 에러 없음, 네트워크 요청 없음, JS로 직접 `.click()` 실행해도 무반응) — 개발/QA용으로 남겨진 미완성 기능으로 추정. 비밀번호가 "4자리 숫자"라는 제약이 처음엔 안내되지 않고 임의 문자열 입력 후 제출해야 에러 메시지로만 드러남(사전 안내 부족).
- KEEP/MODIFY 잠정: 전화번호+PIN 흐름 자체는 고령층 대상으로 적절 (MODIFY: 비밀번호 자릿수 제약을 입력 필드에 사전 안내).

### 2-2. 온보딩(접근성·프로필·보호자 등록)

- 현재 동작: 3단계(접근성 설정 → 개인정보 → 보호자 정보) 순차 진행, 각 단계 "건너뛰기" 가능.
- 문제점: 성별/나이/지역 입력 후 이름 필드만 비어있는 경우가 있었음(포커스 이동 로직이 불안정해 보임 — 재현 시 주의). 이는 프로토타입 특유의 이슈일 수 있어 "확인 필요".
- KEEP: 접근성 우선 온보딩 순서(글자크기→음성→언어) 자체는 타깃 사용자(고령층)에 적합.

### 2-3. 문서 촬영(AI 분석)

- 현재 동작: 사진 촬영하기/사진 불러오기 선택 화면 + 촬영 팁("글자가 선명하게", "빛 반사 적은 곳").
- 문제점: 실제 촬영·업로드·분석 결과는 카메라/파일 접근이 필요해 이번 브라우저 세션에서 **검증하지 못함 (확인 필요)**. 보호자 앱 "받은 연락" 상세 화면 구조로 미루어 분석 결과가 "원문/요약/주의사항/확인할 일" 형태로 구조화된다는 것은 간접 확인.

### 2-4. 문자 내용 요약(수상한 문자 확인)

- 현재 동작: **웹 브라우저에서는 진입 시 "이 기능은 안드로이드 앱에서만 사용할 수 있어요" 안내만 표시되고 실제 기능은 사용 불가.** SMS 접근 권한이 필요한 네이티브 전용 기능으로 확인됨.
- 문제점 없음(웹 프로토타입의 의도된 제약). Flutter 재구현 시 Android에서는 SMS 읽기 권한 기반 구현이 필요하고, iOS는 SMS 접근이 사실상 불가하므로 별도 UX(공유 시트로 문자 붙여넣기 등) 검토 필요.

### 2-5. 주변 복지센터·경로당 찾기

- 현재 동작: 브라우저 geolocation 권한이 없으면 "내 위치를 확인하고 있어요..." 상태로 멈춘 뒤 "주변 시설 정보를 불러오지 못했어요" 에러로 전환. 주소 직접 입력("다른 지역 경로당 찾기") 시 실제 공공데이터로 보이는 결과(구룡경로당/성호경로당/안골경로당, 실제 주소·전화 포함) 반환.
- 문제점: 위치 권한 실패 시 재시도 안내는 있으나("다시 찾기" 버튼), 실패 원인(권한 거부 vs API 오류)을 구분해 안내하지 않음. "주변 복지센터·주민센터" 섹션은 경로당과 달리 결과가 비어있는 상태로 남아있었음(데이터 소스 차이 또는 버그, 확인 필요).
- KEEP: 주소 텍스트 검색 폴백은 위치 권한을 거부하는 고령층 사용자에게 중요한 대안.

### 2-6. 정보 탭(맞춤 정보)

- 현재 동작: 프로필의 나이를 기준으로 "OO님을 위한 정보" 카드 노출(기초연금 신청 안내, 무료 건강검진, 보이스피싱 예방). 상세 화면은 정적 안내 텍스트 + 외부 링크 + 전화번호.
- 문제점: 콘텐츠가 3개로 고정되어 있어 개인화 폭이 제한적(연령대별 세분화 등은 확인 필요). "복지로 홈페이지 열기" 등 외부 링크의 실제 URL은 미검증.
- KEEP: 나이 기반 개인화 자체는 좋은 방향.

### 2-7. 기록/통계(분석 기록, 고지서 통계, 일정)

- 현재 동작: 모두 데이터가 없는 초기 상태에서는 명확한 Empty State 문구 제공("아직 분석한 기록이 없습니다. 문서 찍기나 문자 보기를 이용해보세요." 등).
- 문제점 없음(빈 상태 UX 품질 양호). 실제 데이터가 쌓였을 때의 UI는 미검증(확인 필요).

### 2-8. 긴급 도움(도움 버튼)

- 현재 동작: 홈 화면 우측 하단 상시 노출 플로팅 버튼. 클릭 시 보호자/119/112/118 연결 + "사용법 다시 보기" 모달.
- 문제점: "보호자" 항목 클릭 시 실제 전화 연결(tel: 링크) 여부를 브라우저 환경에서 명확히 확인하지 못함(확인 필요). 그 외 119/112/118은 tel: 링크로 보이며 실제 다이얼은 네이티브 환경에서만 검증 가능.
- KEEP: 상시 노출되는 긴급 도움 버튼 자체는 안전 기능으로 매우 중요.

### 2-9. 쉬운 모드

- 현재 동작: 상단 토글로 즉시 전환. 카드 3개(문서 찍어서 확인하기/수상한 문자 확인하기/가까운 경로당 찾기)를 대형 정사각형 버튼으로, 하단 네비게이션도 큼직한 아이콘+라벨로 재배치. "도움" 버튼이 별도 플로팅이 아니라 하단 네비게이션에 통합되어 상시 노출.
- 문제점 없음. 오히려 매우 잘 설계된 접근성 기능으로 판단됨.
- KEEP(강력): 고령층 타깃 앱의 핵심 차별화 요소로 신규 앱에서도 반드시 유지해야 함.

### 2-10. 설정 / 보호자 연동 설정

- 현재 동작: 설정 화면 내 "보호자 정보"에서 보호자 이름·전화번호 수정 가능. "위험 문자를 발견하면 보호자에게 알릴지 물어보기" 토글(기본값 꺼짐)이 있고, 설명 문구는 **"보호자에게 알릴 때는 이 기기의 문자 앱이 열리고, 내용이 미리 채워집니다. 보내기는 직접 눌러주세요 — 앱이 대신 문자를 보내지는 않습니다."**
- 문제점/모순 후보: 반면 "개인정보 보관 안내" 문서에는 "보호자 앱에는 위험 문자 확인이나 돌봄에 필요한 요약 정보만 전달돼요"라고 되어 있어, 서버를 통한 자동 전달처럼 읽힌다. 실제로 보호자 앱 "받은 연락" 화면 설명도 "부모님이 '보호자에게 알리기'를 누른 결과가 도착합니다"로 되어 있어 **SMS 수동 발송과 서버 기반 전달, 두 메커니즘이 문서상 혼재**되어 있다. → **확인 필요**: 실제 구현 시 (a) 어르신이 버튼을 누르면 서버에 요약이 저장되고 보호자 앱이 이를 조회하는 방식인지, (b) 기기의 SMS 앱으로 실제 문자를 보내는 방식인지, 혹은 두 가지를 병행하는지 기획 확인 필요.
- 기본값이 꺼져있는 것(옵트인)은 어르신의 자기결정권을 존중하는 설계로 보임 — KEEP.

### 2-11. 보호자-어르신 연결

- 현재 동작: 보호자가 어르신 전화번호를 입력하고 "부모님과 연결하기"를 누르면, (프로토타입 한정으로) 같은 브라우저에 로그인된 어르신 계정 정보(이름/나이/지역, 등록된 보호자 이름)를 그대로 불러와 연결 성공 처리.
- 확인 필요: 실제 서비스에서 필요한 SMS 인증/어르신 승인 절차는 이 프로토타입에 없음 — 최소한의 보안 장치이므로 신규 구현 시 필수로 설계해야 함.
- 연결 해제 기능("이 기기의 보호자 연결을 종료합니다")은 보호자 쪽에만 있고, 어르신 쪽에서 보호자를 해제/변경하는 기능은 이번 탐색에서 발견하지 못함(확인 필요).

## 3. 확인 필요 항목 (화면만으로 확정할 수 없음)

- 실제 프로덕션 백엔드/API 구조, 인증 토큰 방식, 서버 저장 스키마 — 이 정적 프로토타입은 브라우저 localStorage 기반으로 동작하는 것으로 보이며 실제 서버 아키텍처를 반영하지 않을 가능성이 높다.
- 위험 문자 감지가 "보호자에게 알리기"를 눌렀을 때 서버 경유인지 기기 SMS 발송인지(위 2-10 참조).
- 어르신 쪽에서 보호자 연결을 해제/변경하는 기능 존재 여부.
- 문서 촬영 실제 업로드·OCR·AI 분석 결과 UI(카메라 접근 불가로 미검증).
- "119/112/118"·"보호자" 긴급 연결 버튼의 실제 통화 연결 동작(브라우저 환경 한계로 미검증).
- "주변 복지센터·주민센터" 결과가 항상 비어 있던 것이 버그인지 데이터 미비인지.
- 소셜 로그인(구글/네이버/카카오)의 실제 OAuth 연동 여부.
- "관리자 테스트 로그인"이 실제로 어떤 기능을 의도했는지(현재는 완전히 비활성).
